# Рабочее соглашение команды

## 1. Цель

Зафиксировать правила совместной работы: когда и как синхронизируемся, где общаемся, как проверяем работу, как решаем разногласия и кто за что отвечает.

## 2. Исходные данные

Команда состоит из одного участника, поэтому соглашение упрощено, как допускает задание: события проводятся в формате «сверка с самим собой», а вместо парного ревью используется самопроверка по чек-листу и контроль преподавателя. Процесс описан в [process.md](process.md).

## 3. Синхронизация

| Событие | Когда | Длительность | Что делаем |
|---|---|---|---|
| Ежедневная сверка | каждый рабочий день, 10:00 (Саратов) | 10 мин | смотрим доску: что сделано вчера, что берём сегодня, что мешает; обновляем статусы карточек |
| Недельное планирование | понедельник, 19:00 | 30 мин | выбираем истории на неделю из «Бэклога» в «Готово к работе» (с учётом DoR и WIP-лимита 2), сверяем прогноз |
| Недельный обзор | воскресенье, 19:00 | 30 мин | считаем, сколько историй завершено, обновляем данные для метрик, фиксируем, что улучшить |
| Контрольная точка по риску | 24.11.2026 | 15 мин | проверяем триггер из [release-plan.md](release-plan.md): если US-07 не в «Готово», US-10 уходит из MVP |

## 4. Каналы связи

- **Решения и вопросы по работе:** комментарии в issue и pull request GitHub (так остаётся история решений).
- **Статус работы:** доска GitHub Projects, единственный источник правды о состоянии историй.
- **Вопросы преподавателю и срочные дела:** мессенджер или почта, принятые на курсе; ответ ожидается в течение рабочего дня.
- **Код:** только через репозиторий, без пересылки архивов.

## 5. Правила работы с кодом и ревью

- Прямые коммиты в `main` запрещены. Каждая история делается в ветке `feature/us-NN-кратко` (например, `feature/us-07-submit-answers`).
- Коммиты небольшие, сообщение начинается с номера истории: `US-07: приём анкеты респондента`.
- На каждую историю один pull request с описанием и ссылкой на issue (`Closes #N`). Размер PR желательно до 400 строк.
- Каждый pull request проходит ревью. Пока в команде один человек, ревью выполняется как **самопроверка по чек-листу не раньше чем через несколько часов после завершения кодирования** (свежим взглядом). Если появится второй участник, PR проверяет он, а автор не сливает свой PR сам.

Чек-лист ревью:

- [ ] PR решает именно ту историю, критерии приёмки выполняются;
- [ ] нет лишних изменений и отладочного кода;
- [ ] есть тесты на основные сценарии и ошибки, тесты проходят;
- [ ] имена понятны, нет дублирования;
- [ ] входные данные проверяются (валидация, коды ошибок);
- [ ] нет секретов, паролей, личных данных;
- [ ] Swagger и README обновлены;
- [ ] выполнен DoD из [process.md](process.md).

## 6. Порядок разрешения разногласий

Разногласия возможны в том числе с самим собой (например, брать ли историю в работу при превышении WIP, оставлять ли US-10 в MVP). Порядок:

1. Сначала сверяемся с зафиксированными правилами: приоритеты (WSJF), DoR, DoD, WIP-лимиты, этот документ. Если ответ есть там, решение принято.
2. Если правила не дают ответа, перечисляем варианты, плюсы и минусы и записываем решение в issue или в `docs/decisions.md` (дата, вариант, причина).
3. Если решение влияет на состав MVP, срок или оценки, оно принимается только на недельном обзоре или контрольной точке, а не по ходу дня.
4. Если спор не решён за один день или меняются требования задания, вопрос выносится преподавателю.
5. Принятое решение пересматривается только при появлении новых данных (например, реальной пропускной способности в ЛР 4).

## 7. Распределение ответственности

Фактически все работы выполняет один участник, но «шляпы» разделены, чтобы не терять взгляд со стороны:

| Роль («шляпа») | Зона ответственности |
|---|---|
| Продукт | видение, карта историй, критерии приёмки, приоритизация WSJF, состав MVP |
| Планирование | сетевой график и PERT, прогноз Монте-Карло, доска и WIP-лимиты, рабочее соглашение |
| Разработка | реализация историй, тесты, документация API |
| Ревью | проверка своего PR по чек-листу, контроль DoR и DoD |

Распределение из задания (участник А: видение, карта историй, сетевой график и PERT, соглашение; участник Б: критерии приёмки, WSJF, рюкзак, Монте-Карло, доска; совместно: оценки, методология, DoR/DoD, взаимная проверка) выполняет один участник целиком; взаимная проверка заменена самопроверкой и ревью преподавателя.

## 8. Выводы

Соглашение задаёт ритм (ежедневная сверка, недельный план и обзор), правила кода и ревью, порядок решения споров и роли. Его можно пересмотреть на любом недельном обзоре, если практика покажет, что правила мешают.
