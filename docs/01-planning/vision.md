# Видение продукта: сервис опросов
 
## 1. Цель
 
Зафиксировать, для кого создаётся сервис опросов, какую проблему он решает, по каким показателям будет понятно, что продукт удался, и что в продукт не входит. Документ служит опорой для бэклога, приоритизации и выбора состава MVP.
 
## 2. Исходные данные
 
| Параметр | Значение |
|----------|----------|
| Тема проекта | Сервис опросов: создание анкет, типы вопросов, прохождение, агрегирование результатов, экспорт |
| Исполнитель | Один человек (упрощённые нормы: 10+ историй в бэклоге, 4–6 историй в MVP) |
| Срок | Один семестр, четыре этапа (ЛР 1–4) |
| Архитектура | Серверная часть с REST API, хранилище данных, запуск одной командой `docker compose up` |
| Интерфейс | Swagger/OpenAPI (допущение; при желании можно добавить простую веб-страницу позже) |
 
## 3. Ход выполнения
 
### 3.1. Краткое описание продукта
 
Для **авторов опросов** (преподавателей, организаторов мероприятий, студентов-исследователей), которым нужно быстро собрать мнения группы людей и получить результаты без ручной обработки таблиц, **сервис опросов** — это веб-сервис с API, позволяющий создать анкету, раздать ссылку, собрать ответы и сразу увидеть сводку и выгрузку в CSV. В отличие от обычных таблиц и самодельных форм, сервис хранит структуру вопросов и сам считает агрегаты.
 
### 3.2. Целевые пользователи
 
| Роль | Кто это | Чего хочет | Как использует сервис |
|------|---------|------------|------------------------|
| **Автор опроса** (основной пользователь) | Преподаватель, организатор мероприятия, студент, проводящий исследование, владелец небольшого проекта | Быстро составить анкету, получить ответы и понятные итоги | Создаёт опрос и вопросы, публикует, смотрит результаты, выгружает данные |
| **Респондент** | Студент, участник мероприятия, клиент | Быстро и без регистрации ответить на вопросы | Открывает ссылку, отвечает, отправляет |
 
Типичные примеры: преподаватель собирает обратную связь по курсу; организатор оценивает мероприятие; студент проводит опрос для курсовой.
 
### 3.3. Проблема
 
Сейчас опросы чаще всего делают в общих таблицах или в сторонних конструкторах форм. Это даёт несколько неудобств:
 
1. **Ручная обработка результатов.** Ответы приходят «сырыми», проценты и распределения приходится считать самостоятельно.
2. **Нет контроля над данными.** Данные хранятся у стороннего сервиса, выгрузка и формат определяются им.
3. **Непрозрачная структура.** В таблицах трудно задать типы вопросов, обязательность полей и проверить корректность ответа (например, значение вне шкалы).
4. **Сложная автоматизация.** Нет API, через который результаты можно забрать в свой скрипт или отчёт.
Сервис решает это: вопросы имеют типы и правила проверки, агрегаты считаются автоматически, данные доступны через API и экспорт.
 
### 3.4. Ключевые сценарии
 
| № | Сценарий | Роль | Результат |
|---|----------|------|-----------|
| С1 | Создание опроса: название, описание, набор вопросов | Автор | Черновик опроса сохранён |
| С2 | Добавление вопросов двух типов: один вариант и шкала (1–5), с возможностью сделать вопрос обязательным | Автор | Вопросы с правилами проверки ответов |
| С3 | Публикация опроса и получение ссылки | Автор | Опрос доступен респондентам по ссылке |
| С4 | Прохождение опроса: ответить на вопросы и отправить | Респондент | Ответ сохранён, обязательные вопросы проверены |
| С5 | Просмотр сводки: число ответов, распределение по вариантам, среднее по шкале | Автор | Агрегированные результаты |
| С6 | Экспорт всех ответов в CSV | Автор | Файл для дальнейшего анализа |
| С7 | Закрытие опроса (приём ответов остановлен) | Автор | Новые ответы не принимаются |
 
Сквозной путь автора: **создать → наполнить вопросами → опубликовать → собрать ответы → посмотреть итоги → выгрузить**. Он ляжет в основу карты историй (задание 1.2).
 
### 3.5. Критерии успеха
 
Показатели измеримы и проверяются на готовом MVP (часть замеров совпадает с нагрузочными тестами ЛР 3).
 
| № | Показатель | Целевое значение | Как измеряем |
|---|------------|------------------|--------------|
| К1 | Время создания опроса из 5 вопросов через API/Swagger | не более 5 минут при первом использовании | Ручной замер по сценарию С1–С3 |
| К2 | Время получения сводки по опросу со 100 ответами | p95 не более 1 с | Скрипт нагрузочного теста в `load/` |
| К3 | Экспорт 1000 ответов в CSV | не более 5 с, данные совпадают с БД | Автотест и замер времени |
| К4 | Сервис запускается с нуля | одной командой `docker compose up`, не более 5 минут | Проверка на чистой машине |
 
### 3.6. Что не входит в продукт
 
Чтобы MVP уложился в семестр и ёмкость одного исполнителя, сознательно **не делаем**:
 
- условную логику («если ответил А, показать вопрос Б»);
- визуальный конструктор с перетаскиванием и редактор тем оформления;
- регистрацию через соцсети и внешние сервисы (OAuth);
- рассылку приглашений по почте и мессенджерам;
- платные тарифы и оплату;
- вопросы с выбором нескольких вариантов и со свободным текстом (откладываются на следующие версии: в объём бэклога одного исполнителя они не вошли);
- многоязычность интерфейса;
- мобильные приложения;
- совместное редактирование опроса несколькими авторами;
- гарантированную анонимность на уровне юридических требований (в MVP ответы не привязываются к личности, но формальный аудит не проводится).
### 3.7. Допущения и риски
 
| Тип | Описание | Что делаем |
|-----|----------|------------|
| Допущение | Респондент отвечает без регистрации, по ссылке | Закладываем в истории; при смене решения пересмотрим бэклог |
| Допущение | Автор идентифицируется простым способом (например, токен) | Решим при проработке историй |
| Риск | Время на изучение инструментов (GitHub, Docker) съест ёмкость | Заложить буфер в расчёт ёмкости (задание 1.4) |
| Риск | Агрегирование и экспорт сложнее, чем кажется | Оценить трёхточечно в задании 1.3 |
